# v1.9.0 — `[Execute]` Obeys `[Remote]`

**Released:** 2026-09-08
**Breaking changes:** Yes — behaviour, and one generated signature. A bare `[Execute]` is no longer always remote; where it runs now follows the same rules as every other operation, so one that needs the server must add `[Remote]`. Separately, a class-level `[Execute]` under `[AuthorizeFactory]`/`[AspAuthorize]` now generates `Task<T?>` where it generated `Task<T>`. See [Migration Guide](#migration-guide).

> **Pre-stable API note.** v1.9.0 is an intentional minor bump carrying a breaking change, and it departs from the [API Stability Commitment](v1.0.0.md#api-stability-commitment) published in v1.0.0 — which promises that minor releases are additive and counts generated code shapes as part of the public surface. The 1.x line is still settling where factory operations run; v1.1.0, v1.4.0 and v1.5.0 each broke under a minor bump for the same reason. If you depend on `[Execute]` placement, read the [Breaking Changes](#breaking-changes) section before upgrading.

## Overview

`[Execute]` was welded to remote execution. Whatever you wrote, the generator emitted a remote delegate and a guarded local one, so an `[Execute]` always crossed to the server and `[Remote]` on it was documented as decorative.

It no longer is. **`[Execute]` obeys `[Remote]` like every other factory operation.** Without `[Remote]` there is no remote delegate and no endpoint: the method runs on whichever tier resolves it, takes its `[Service]` parameters from that tier's container, and — on a Blazor WASM client published with trimming — ships and runs in the browser. With `[Remote]`, placement is unchanged from v1.8.1; the one exception is a class-level `[Execute]` under authorization, whose generated return type is now nullable (see [Bug Fixes](#bug-fixes)).

That makes a bare `[Execute]` the shape for client-side computation that must not round-trip, which is what this release exists to enable. It also means a bare `[Execute]` that quietly relied on running server-side will now fail on the client at call time.

One bug fix rides along, in the same area.

## What's New

### A bare `[Execute]` runs where it is called

```csharp
[Factory]
public static partial class TallyCommand
{
    // No [Remote] — runs on whichever tier resolves the delegate,
    // with that tier's services.
    [Execute]
    private static Task<decimal> _Total(decimal baseSalary, decimal bonus,
        [Service] ISalaryCalculator calculator)
        => Task.FromResult(calculator.Calculate(baseSalary, bonus));
}
```

On a static factory the generator emits **one unguarded local registration in every factory mode** and no remote registration. The delegate resolves `ISalaryCalculator` from the container that runs the call, so the service must be registered on that tier — on a client, that means client DI.

A class factory reaches the same place by a different route, since `[Execute]` there returns the containing type and generates a factory-interface method rather than a delegate:

```csharp
[Execute]  // no [Remote]
public static Task<ClassExecuteDemo> ScoreLocally(string input, [Service] ITextScorer scorer)
```

The generator emits a **Local method only** — unguarded, with no remote delegate and no endpoint — and resolves `[Service]` parameters from the factory's own container.

**The body is genuinely on the client.** The trimming gate publishes a trimmed client and asserts, for three matched pairs — static sync, static async, class async — that the `[Remote]` sibling's body is **absent** and the bare sibling's body is **present**, then resolves the bare member from the trimmed client's own container and runs it. Both halves are measured, not inferred; a guard creeping back onto a bare `[Execute]` turns the gate red.

### The server refuses a crafted request naming a bare delegate

Because a bare `[Execute]` has no remote registration, a client never sends a request for it. The generated registrar also declares the delegate type in a local-only registry, so the server's delegate handler refuses a request that names one, exactly as it refuses an unknown delegate.

## Breaking Changes

### Where a bare `[Execute]` runs

`[Remote]` decides placement, and visibility carries the same meaning it carries on every other operation:

| Declaration | Where it runs | Body trimmed from a client? |
|---|---|---|
| **Static factory** — `[Remote, Execute] private static` | Server | Yes |
| **Static factory** — `[Execute] private static` | Wherever the delegate resolves | **No — that is the point** |
| **Class factory** — `[Remote, Execute]` (`public`/`internal static`) | Server | Yes |
| **Class factory** — `[Execute] public static` | Wherever the factory resolves | **No** |
| **Class factory** — `[Execute] internal static` | **Server only** — guarded, as any `internal` operation | Yes |

Two qualifications matter before you change anything:

- **`internal static` on a class factory is unaffected.** Without `[Remote]` it is still server-only: the generated local method carries the `IsServerRuntime` guard and the member is carried on the factory interface with the `internal` modifier rather than promoted. It needs no migration.
- **Authorization still forces the server.** A bare `[Execute]` carrying `[AspAuthorize]`, or whose `[AuthorizeFactory]` auth method is itself `[Remote]`, still crosses — the auth terms decide placement. A non-`[Remote]` `[AuthorizeFactory]` method runs alongside the call on whichever tier it landed on.

**What breaks:** a bare `[Execute]` — `private static` on a static factory, `public static` on a class factory — that resolves a `[Service]` only the server registers. It used to reach the server anyway; now it runs where it was called and throws a DI resolution error there. The code still compiles.

### One generated signature changed

A class-level `[Execute]` under `[AuthorizeFactory]` or `[AspAuthorize]` now generates `Task<T?>` where it generated `Task<T>`. See [Bug Fixes](#bug-fixes) for why. If you build with `TreatWarningsAsErrors`, call sites that assign the result to a non-nullable local will now fail until you handle the null a denial returns.

`[Remote, Execute]` is otherwise unchanged from v1.8.1, including the non-async wrapper carrying the guard.

## Bug Fixes

### Class-level `[Execute]` under authorization returned null through a non-nullable signature

A class-level `[Execute]` combined with `[AuthorizeFactory]` or `[AspAuthorize]` generated a factory method declared `Task<T>` while returning `Authorized<T>.Result` — which is `default` when the check denies. Two consequences, depending on your build:

- **With `TreatWarningsAsErrors`** (this repository's setting) the generated file failed to compile with `CS8603: Possible null reference return`. The shape was unbuildable.
- **Without it**, CS8603 was a warning, so the shape *did* build — and a denied call handed `null` back through a signature that promised non-null.

The generator now applies the same rule the Read path has always applied: an authorized method's return type is nullable. So this shape **now compiles, and its result is typed nullable** — it was not previously impossible, only unsound. Both bare and `[Remote]` class-level `[Execute]` were affected.

## Deployment

**Upgrade both tiers together.** A v1.8.1 client still emits a remote registration for a bare `[Execute]`, and a v1.9.0 server refuses that request as naming a local-only delegate. Client and server built from one solution upgrade together by construction; if you deploy them separately, do not leave a 1.8.1 client talking to a 1.9.0 server.

## What this release does not claim

- **Interface-factory bodies are not established as trimmed.** Unchanged from v1.7.0: that leg reaches its implementation through interfaces, so a client-side trimmed test reads "absent" either way. No leak is observed and none is proven.
- **Interface factories cannot carry `[Execute]` at all.** They stay always-remote, enforced by **NF0106**. Nothing in this release changes that; the placement rule above is about class and static factories.
- **`[AspAuthorize]` on a *static-factory* `[Execute]` is collected but not enforced.** It decides placement — the call crosses — but no policy check is rendered. Pre-existing and unchanged here; tracked as [#91](https://github.com/NeatooDotNet/RemoteFactory/issues/91).
- **Generated code relies on your project's `ImplicitUsings`.** Generated factories name `Task`, `CancellationToken`, `IServiceProvider` and `InvalidOperationException` unqualified. Every SDK template since .NET 6 enables the feature, so this is latent rather than urgent; tracked as [#97](https://github.com/NeatooDotNet/RemoteFactory/issues/97).

## Migration Guide

**One audit for placement, plus two things to check afterwards.**

Find every `[Execute]` without `[Remote]` that is `private static` on a static factory or `public static` on a class factory, and check its `[Service]` parameters. If any is a service only the server registers — a repository, a `DbContext`, an outbound client — add `[Remote]`:

```csharp
// Before v1.9.0 this reached the server regardless. Now it runs where it is called.
[Remote, Execute]
private static Task<TransferResult> _TransferEmployee(
    Guid employeeId, [Service] IEmployeeRepository repository) { ... }
```

**Check the authorization method's parameters too.** An `[AuthorizeFactory]` method that is **not** itself `[Remote]` does not force the call to the server, so it now runs client-side alongside the `[Execute]` it guards — and *its* `[Service]` parameters resolve from the client's container. A permissions repository injected into the auth method will throw there even when the `[Execute]` method's own signature is clean. Either add `[Remote]` to the auth method (which forces the whole call to the server) or make its services client-resolvable.

**Leave alone:**

- `internal static` `[Execute]` on a class factory — already server-only.
- Any `[Execute]` carrying `[AspAuthorize]`, or whose `[AuthorizeFactory]` method is `[Remote]` — authorization already forces the server.
- Anything already carrying `[Remote]`.

**If you use class-level `[Execute]` with authorization**, its factory method now returns `Task<T?>`. Handle the null a denial produces; under `TreatWarningsAsErrors` your build will point at the call sites.

**If a bare `[Execute]` is what you wanted all along** — a scoring rule, a planner, any computation that must not round-trip — you now have it, and its `[Service]` dependencies must be registered on the client. That is the capability this release exists for.

## Testing

The placement rule is pinned at three tiers.

**Integration** — both shapes proven local: a bare `[Execute]` on a static factory and on a class factory resolves and runs on the client, with a wire stand-in installed that fails the test if anything crosses, plus a `[Remote, Execute]` control that must hit that stand-in. The authorization interplay is pinned on the class shape: `[AspAuthorize]` forces remote, a non-`[Remote]` `[AuthorizeFactory]` runs alongside, and a denial returns null.

**Trimmed harness** — `RemoteFactory.TrimmingTests` publishes a trimmed client and its CI gate asserts three matched absent/present pairs (static sync, static async, class async), each controlled for async-ness, then invokes each bare member on the trimmed client through a client-registered service. The new assertions were observed **red** against a variant in which the bare targets carry `[Remote]`, with every incumbent check still green, before they were trusted.

**Unit** — generated-code shape: the class-level placements on one class (`public static` unguarded, `internal static` guarded and not promoted, `[Remote] internal static` guarded and promoted), and the NF0105 static exemption in both its `[Execute]` and `[Create]` forms.
