# v1.10.0 — A Denial Always Says Something

**Released:** 2026-09-09
**Breaking changes:** No. One visible behaviour change: `NotAuthorizedException.Message` was previously the empty string when an authorization method returned a bare `false`; it now always carries text. Code that compares that message to `""` would need to change — see [Behaviour Notes](#behaviour-notes).

## Overview

`NotAuthorizedException` could be thrown with an **empty** `Message`. Any authorization method returning a plain `false` produced one, and that is the common shape — `bool` returns have no way to carry a reason, while only the `string?` forms do.

An empty exception message is worse than an unhelpful one. A consumer's nightly job hit exactly this: the refusal was correct (a background job legitimately lacked a role), the job caught the exception and logged it through `ILogger.LogError`, and **Application Insights rejected the record at ingestion** because exception telemetry requires a non-empty message. Measured across one two-second run, the app emitted 206 Information, 3 Warning and 4 Error records; App Insights received 206, 3, and **zero**. Nothing was sampled — every record without an exception arrived intact. Four records a night vanished for about four months, and diagnosing it required pulling raw container logs off the host.

This release makes the message never empty, and makes it useful: it names what was refused.

## Bug Fixes

### `NotAuthorizedException` no longer carries an empty message

`Authorized(bool)` leaves `Message` null, and the implicit `bool` → `Authorized` conversion routes through it, so a `bool` authorization method reached the exception with nothing to say. The exception then did `?? ""`.

Now, when no reason was supplied, the message names the operation and type:

```
Authorization denied for operation Save on IVisitV2; no reason was supplied.
```

and on an interface factory — where one method can run several authorization methods — it names the one that refused:

```
Authorization denied for operation GetItem on IRepository (IRepositoryAuth.CanAccessItem); no reason was supplied.
```

**A message your authorization method did supply is used verbatim**, exactly as before. It is never prefixed or decorated. Whitespace-only messages are treated as absent, since `new Authorized("")` and the string conversion both admit a denial that says nothing.

The wording deliberately says *no reason was supplied* rather than stopping at the operation, so an on-call engineer can tell "the authorization method returned bare `false`" from "the reason went missing in transit". It also matches the framework's own `AuthorizationDenied` log message (event id 5002), so the exception and the log line correlate in a search.

**Two tiers, and which one you get depends on whether you rebuild.** Generated code compiles into your assembly, so:

- **Update the package only** — the runtime supplies `Authorization denied; no reason was supplied.` The telemetry drop stops immediately, with no rebuild.
- **Update and rebuild** — generated call sites additionally pass the operation and type, so you get the fuller messages above.

## What's New

### `NotAuthorizedException.Context` and `.Authorized`

```csharp
catch (NotAuthorizedException ex)
{
    logger.LogWarning(ex, "Refused: {Context}", ex.Context);  // "operation Save on IVisitV2"
    var hadAccess = ex.Authorized?.HasAccess;                 // the result as the auth method returned it
}
```

`Context` carries the operation and type as a property whether or not the authorization method supplied its own message, so structured logging can capture what was refused without parsing `Message`. A new constructor overload, `NotAuthorizedException(Authorized, string?)`, is what generated code calls; the existing `(Authorized)` overload is unchanged and still works, so already-compiled consumer code keeps binding to it.

**Why this is a minor release and not a patch.** The [API Stability Commitment](v1.0.0.md#api-stability-commitment) published in v1.0.0 says patch releases carry no API changes. A new public constructor and two new properties are additive API, so this ships as a minor bump even though its substance is a bug fix.

## Behaviour Notes

**Previously-empty messages are now non-empty.** That is the fix, but it is visible: any code asserting `ex.Message == ""` or `string.IsNullOrEmpty(ex.Message)` on a denial will change behaviour. Code that logs or exports the message — the overwhelmingly common case — gets strictly better.

**Messages your authorization methods supply are untouched.** If you return `string?` from your auth methods, nothing about your messages changes.

**A denial on `Save` may name the operation without naming the check.** The `Save` wrapper receives an already-decided result from the underlying `Insert`/`Update`/`Delete` path, so it reports `operation Save on {Type}` without identifying which authorization method refused. Interface factories, which throw at the check itself, do name it.

## What this release does not claim

- **Interface-factory `[Remote]` denials still do not survive a real HTTP hop.** The exception is thrown server-side and is not mapped into the response, so an HTTP client sees a 5xx rather than a `NotAuthorizedException` — the improved message included. In-process test harnesses hide this. Tracked as [#103](https://github.com/NeatooDotNet/RemoteFactory/issues/103); unchanged by this release.
- **Two non-authorization paths still throw `NotAuthorizedException` on `Save`.** A `bool`-returning `Insert`/`Update`/`Delete` returning `false`, and a target that is both new and deleted, both surface as a denial — now with the same "no reason was supplied" wording, which is honest but imprecise. Pre-existing; tracked as [#104](https://github.com/NeatooDotNet/RemoteFactory/issues/104).

## Migration Guide

**None required.** Update the package; the empty-message problem is gone. Rebuild to get the operation and type in the message as well.

If you want to know *why* a call was refused rather than just *what* was refused, return `string?` from the authorization method instead of `bool` — that message reaches `NotAuthorizedException.Message` verbatim, and always has.

## Testing

`NotAuthorizedExceptionTests` covers the message construction directly: bool denial with and without context, denial through the implicit `bool` conversion (the path the generator actually takes), whitespace-only messages, a null `Authorized`, `Authorized<T>` in all three of its shapes, and — the assertions that keep the fix honest — that a supplied message survives verbatim even when context is present.

`NotAuthorizedContextEmissionTests` pins the generated output for both legs, asserting the exact literal each throw site emits and that the old context-less form is gone. Integration tests assert the message and `Context` on a class-factory `Save` denial and an interface-factory `bool` denial; the class-factory test deliberately arranges Fetch-then-deny rather than create-then-delete, because a target that is both new and deleted short-circuits before any authorization method runs and would pass the test without exercising the path it claims to.

The four pre-existing tests that assert on author-supplied denial messages are untouched and green.
