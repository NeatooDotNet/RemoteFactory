# v1.10.7 — Static-Factory Authorization Enforced; Ordinal Keeps Shared and Back References

**Released:** 2026-10-16
**Breaking changes:** No. Rebuild, and deploy client and server together.

## Overview

Five fixes, two in the generator's output that change what an application does:

- **Security fix.** `[AuthorizeFactory<T>]` on a static factory's `[Execute]` was never checked. It is now enforced, and a refusal throws `NotAuthorizedException`.
- **The Ordinal format keeps reference identity.** A `[Factory]` object shared by two properties no longer arrives as two copies, and a back reference no longer fails with "possible object cycle" (#133). The Ordinal wire shape changes, so client and server must run the same version.

The other three: a trimmed client's Save no longer turns into an Insert for a class factory without an ordinal converter; a remote call's relay batch carries only its own events; and the client's `HttpRequestException` carries the status code.

This release also ships the EXSET documentation rewrite: every C# example in the docs, the README and the skill is now compiled and tested code from `src/Design`.

## Bug Fixes

### `[AuthorizeFactory<T>]` on a static factory's `[Execute]` was never enforced

On a static factory, the generator used the `[AuthorizeFactory<T>]` class only to decide whether an `[Execute]` call goes to the server. The auth methods never ran, so every caller got through. The generated delegate now resolves the auth class, runs its matching methods before the command (and before any `[AspAuthorize]`), and throws `NotAuthorizedException` naming the refused check. The auth class is registered the way it is for class and interface factories, which also keeps it through IL trimming.

Exposed: any static factory whose `[Execute]` relied on `[AuthorizeFactory<T>]` to refuse a caller. `[AspAuthorize]` on a static `[Execute]` was already enforced from v1.10.5.

### Ordinal format: shared references duplicated, back references failed (#133)

The generated ordinal converter wrote a `[Factory]` class as a bare array with no `$id`/`$ref`. So in the default Ordinal format:
- `team.Lead` and `team.Members[0]`, one instance on the server, arrived as two;
- `member.Team = team` recursed until the serializer threw "a possible object cycle was detected". On a fetch that failed on the server, so over HTTP the call was a 500.

The Named format was not affected.

The converter now writes an object's first appearance as `{"$id":"n","$values":[...]}` and each later one as `{"$ref":"n"}`. The ids come from the same `NeatooReferenceResolver` as the `$id`s on collections in the graph. To make back references work, a class whose ordinal properties all have plain setters is now built and registered before its properties are read.

A class with an `init` or `required` property is still built from its properties, once they are all read. A shared reference to it resolves, but a back reference into it throws a `JsonException` that names the type and says what to change. Named handles that case. Records are unchanged: a bare array with no `$id`/`$ref`, as they bypass reference tracking in the Named format too.

### A trimmed client turned every Save into an Insert for some class factories

This affected a `[Factory]` class that gets no generated ordinal converter: one whose constructor takes services, one that is not `partial`, or one that is nested. On a publish-trimmed client nothing referenced that class's property accessors, so the trimmer removed them. The object serialized as `{}` in both formats, `IsNew`/`IsDeleted` were lost, and the server routed every Save to Insert. The class-factory registrar now emits `DtoConstructorRegistry.PreserveProperties<T>()` for that shape. It roots public properties and fields only, so `[Remote]` method bodies still trim.

### A relay batch could carry another call's events

When one server scope served more than one remote call, a response could carry events an earlier call raised, including those of a call that failed. A host that shares a scope across calls, such as an in-process test harness, could hit this. ASP.NET Core gives each request its own scope, so it did not. The server now clears the scope's event collector as each remote call begins.

### `HttpRequestException.StatusCode` was null

When the server answered a remote call with a non-success status, the client threw `HttpRequestException` without the status code. It now passes `response.StatusCode`, so `ex.StatusCode` reads the status (403, 404, 500, ...).

## What's New

Nothing new for application code. The generated code calls two new members in `Neatoo.RemoteFactory.Internal`, `NeatooOrdinalReferences` and `DtoConstructorRegistry.PreserveProperties<T>()`; they are not for direct use.

## Migration Guide

- **Rebuild every assembly that has `[Factory]` types.** All five fixes need the new generator output or the new library, and the authorization and reference fixes need both.
- **Deploy client and server together.** A v1.10.7 server's Ordinal output wraps each `[Factory]` class in `{"$id":...,"$values":...}`, and a v1.10.6 client cannot read it. A v1.10.7 server still reads the bare arrays a v1.10.6 client sends. A Blazor WebAssembly client the browser has cached is the case to watch.
- **A static `[Execute]` under `[AuthorizeFactory<T>]` can now refuse.** If a caller relied on the old behaviour, it now receives `NotAuthorizedException`. Fix the auth method's rule, or remove the attribute from the operation.
- **A back reference into a class with `init` or `required` properties fails in the Ordinal format.** Before, any back reference failed. Give such a class plain setters, or keep the child from pointing back.
