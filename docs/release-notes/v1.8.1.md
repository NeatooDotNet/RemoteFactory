# v1.8.1

**Released:** 2026-09-01
**Breaking changes:** No — but see [Behaviour Notes](#behaviour-notes); a path that delivered
nothing now delivers events.

## Overview

Two fixes.

A **v1.8.0 regression**: a `[FactoryEventHandler<T>]` whose `[Service]` parameter is a
factory interface generated by the same build — `[Service] IPlanFactory` next to
`[Factory] Plan` — failed to compile with CS0400. Code that compiled under v1.5.0 broke on
upgrade.

And a long-standing gap: a client-initiated `IFactoryEvents.Raise` never relayed anything
back to the client. The server collected the events, serialized them into the response, and
the client threw the whole response away — silently, with no exception and no log.

## Bug Fixes

### `[Service]` parameter of a generated factory interface no longer emits CS0400 (v1.8.0 regression)

```csharp
[FactoryEventHandler<TherapyStarted>]
public static partial class AutoApproveHandler
{
    internal static Task Handle(TherapyStarted evt, [Service] IPlanFactory planFactory) { ... }
}
```

`IPlanFactory` is produced by the same generator run, from `[Factory] Plan`. Under v1.8.0
this generated `sp.GetRequiredService<global::IPlanFactory>()` — no namespace — and the
consumer's build failed:

```
error CS0400: The type or namespace name 'IPlanFactory' could not be found in the global namespace
```

v1.8.0 made the handler pipeline's `[Service]` parameter types `global::`-qualified so the
generated registration binds correctly under a shadowing consumer namespace. That is a real
fix for types the semantic model can resolve. But a factory interface the same run is about
to generate does not exist in the input compilation: its symbol is an error type whose display
string is the bare identifier, and `global::` on a bare identifier means the global namespace.

Error-type parameters are now emitted **exactly as the consumer wrote them** — qualifier
included, which the symbol had already lost — and resolve through the `using` directives the
generator copies into the generated file once the interface exists. That is how every other
renderer's `[Service]` parameters have always been emitted; the class-factory path captures
from syntax and never asks the symbol, which is why `[Fetch]` methods taking the same
interface kept compiling. Resolved types stay `global::`-qualified, and the shadowing fixtures
still pass.

Handlers whose `[Service]` parameters are hand-written interfaces were never affected.

Reported while upgrading zTreatment from 1.5.0 to 1.8.0.

### Client-initiated `Raise` now relays its response batch

`MakeRemoteDelegateRequest.ForDelegateEvent` awaited the HTTP round-trip and discarded the
`RemoteResponseDto`. It never read `RelayedEvents` and never touched `IFactoryEventRelay` —
that logic lived only in the factory-call path.

The server was always correct. `HandleRemoteDelegateRequest` attaches the request-scoped
collector's contents to the response without branching on which delegate ran, so a
`RaiseFactoryEventRemote` request got the same batch a `[Remote]` factory call does. It was
built, serialized, and put on the wire on every client raise. Only the client half was
missing.

What this cost in practice: a `[FactoryEventHandler<T>]` that raised a client-bound event in
response to a client-initiated `Raise` reached nobody. `RaiseOptions.None` documents itself
as "capture the event for relay back to the client," and on this path that promise was never
kept — while `ServerOnly` faithfully delivered the same nothing.

The relay dispatch is now a single shared implementation called from both paths. The
divergence between them is what caused this.

## Behaviour Notes

**If you use client-side `Raise` and register an `IFactoryEventRelay`, you will start
receiving batches you were not receiving before.** That is the fix, but it is a visible
change — a relay that fans out to a UI bus will now see events on this path for the first
time.

**The batch includes the caller's own event.** This is deliberate, not an echo artifact:
`RemoteFactoryEvents.Raise` dispatches nothing locally, so the client's relay has not
otherwise seen the event, and relaying it back is the only way client-side handlers observe
it at all. Pass `RaiseOptions.ServerOnly` to suppress the batch entirely — handlers still run
server-side and the client receives one invocation with `events.Count == 0`.

**The relay contract now reads "once per remote round-trip"** rather than "once per
`[Remote]` factory call". There are two kinds of round-trip: a factory call, and a
client-initiated `Raise`. Ordering, exception isolation, and the empty-batch guarantee are
unchanged on both.

**Client-side `Raise` is now documented as a supported path.** It was previously listed as an
anti-pattern whose stated reason — "events raised outside that scope have no collector and
cannot be relayed" — was factually wrong: the server's `RaiseFactoryEventRemote` delegate
calls the server's own `IFactoryEvents.RaiseUntyped`, which collects normally. The guidance
that replaces it is narrower and true: raising inside a factory method shares that method's
scope, `DbContext`, and transaction, and costs no second round-trip. A client raise is a
separate round-trip in its own request scope and cannot roll the preceding call back. Prefer
the factory method when the event belongs to the operation.

**A client raise is still not fire-and-forget** — unchanged since v1.1.0. `Raise` returns only
after every server handler completes, and a handler exception propagates back to the client,
in which case nothing relays for that call.

## Testing

**The generator regression** had no fixture: nothing in the repo declared a handler taking a
generated factory interface, so the hostile-namespace fixtures that caught three other
qualification defects in v1.8.0 could not have caught this one.
`RelayHandlerGeneratedServiceTypeTests` adds a `[Factory]` class and a handler injecting its
interface in one compilation — bare and partially-qualified spellings — and asserts the
output compiles. Both compile tests fail with CS0400 in the handler's generated file on the
v1.8.0 generator and pass on this one.

**The relay gap:** the production `MakeRemoteDelegateRequest` had **no direct test at all**,
which is how it survived: the integration suite substitutes a test double for `IMakeRemoteDelegateRequest` to
avoid HTTP, replacing the entire class under test. Those tests pin the end-to-end contract but
cannot see a defect in the production client.

`MakeRemoteDelegateRequestRelayTests` closes that hole by stubbing only the HTTP delegate. Its
two `ForDelegateEvent` tests fail by 30-second timeout before this change and pass in ~400 ms
after; `ForDelegateNullable_StillRelaysTheResponseBatch` is green throughout as a positive
control on the harness.

Also added: five integration tests covering the end-to-end semantics (echo, handler-raised
events, `ServerOnly`, an `AfterCommit` handler raising during the framework drain, and the
throwing-handler path), and one Design test as the requirements record.
