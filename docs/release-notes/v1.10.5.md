# v1.10.5 — Registering Twice Is Safe; `[AspAuthorize]` Guards Static Commands

**Released:** 2026-10-13
**Breaking changes:** No. Read the migration note on `[AspAuthorize]` before updating a server whose static commands carry it.

## Overview

Two server-side fixes that ship together, because the second depends on the first.

- `AddNeatooRemoteFactory` can now run more than once on one service collection. A Neatoo server that also called `AddNeatooAspNetCore` lost every remote Save.
- `[AspAuthorize]` on a static-factory `[Execute]` is now enforced. Before, it moved the call to the server and checked nothing.

Enforcing the policy needs `IAspAuthorize`, which only `AddNeatooAspNetCore` registers. On a Neatoo server, that is the second registration the first fix makes safe.

## Bug Fixes

### `AddNeatooRemoteFactory` called twice no longer breaks the server (#117)

A Neatoo server on ASP.NET Core reaches `AddNeatooRemoteFactory` twice:
1. Neatoo's `AddNeatooServices(NeatooFactory.Server, ...)` calls it with the domain assembly plus Neatoo.dll, then swaps the JSON converter factory for Neatoo's own.
2. `AddNeatooAspNetCore(...)` calls it again.

The method registered with `Add`, so the second call won:
- it replaced `IServiceAssemblies` with a list that lacked Neatoo.dll;
- it put the interface converter factory back beside Neatoo's.

The server then could not deserialize any Neatoo entity the client sent. Every remote Save failed, while Fetch kept working. Calling the two in the opposite order happened to work, so the outcome depended on line order in `Program.cs`.

The first call now registers everything. A later call in the same mode adds only what is new:
- its assemblies join the existing `IServiceAssemblies`, and their factories are registered;
- every other registration stands, including a converter factory the host replaced.

Serialization options passed explicitly replace the registered ones; the overloads without options keep them. A later call in a different `NeatooFactory` mode throws `InvalidOperationException`, because one container cannot be both client and server.

### `[AspAuthorize]` on a static-factory `[Execute]` is enforced (#91)

```csharp
[Factory]
public static partial class AdminCommands
{
    [Remote, Execute]
    [AspAuthorize("RequireSuperUser")]
    private static Task<int> _Backfill(int batchSize, [Service] IBackfillService service) { ... }
}
```

The generator collected the attribute but rendered no check, so any caller who reached `/api/neatoo` ran the command. The server's delegate now calls `IAspAuthorize` with forbid before it resolves services or runs the method:
- an allowed call runs as before;
- a refused call never runs, and the server answers 403, which the client raises as `HttpRequestException`. Interface factories already behave this way: a delegate has no `Authorized<T>` to carry a refusal back.

All `[AspAuthorize]` attributes on the method must pass. A bare `[Execute]` (no `[Remote]`) with `[AspAuthorize]` was already forced to the server, and is now checked there too.

## What's New

Nothing new in the public API.

## Migration Guide

- **Static commands with `[AspAuthorize]` are now checked.** A server where they ran unchecked will start refusing callers who fail the policy. Make sure the policy names exist in `AddAuthorization`.
- **The check needs `IAspAuthorize`.** Without it, such a command throws "No service for type 'Neatoo.RemoteFactory.IAspAuthorize' has been registered". Register it with `AddNeatooAspNetCore(...)`. On a Neatoo server, call it before or after `AddNeatooServices(NeatooFactory.Server, ...)`: both orders now work.
- **Remove ordering workarounds.** If you called `AddNeatooAspNetCore` before `AddNeatooServices` only to dodge #117, or left it out for that reason, either order is now safe.
- **Mixed modes now throw.** If one service collection called `AddNeatooRemoteFactory` in two different modes, it now throws at startup. That configuration never worked.

## Testing

- Registration (unit):
  - a Neatoo-style first call plus a second call keeps the first call's assemblies and the host's converter factory;
  - a new assembly on the second call joins the existing list;
  - a repeat with the same assemblies registers nothing;
  - options are kept without an explicit argument and replaced with one;
  - a mode clash throws.
  - All seven failed before the fix.
- Static `[AspAuthorize]` (integration, serializing client/server containers, with a stand-in `IAspAuthorize` that throws `AspForbidException` as the real one does):
  - allowed calls, with and without a result, and a bare `[Execute]`, run on the server after the check;
  - every attribute is checked with forbid set;
  - refused calls never run the method.
  - All six failed before the fix. The containers carry no HTTP status, so the 403 itself is not asserted here.
- `Neatoo.RemoteFactory.sln`: 841 unit and 648 integration tests pass (5 skipped, all pre-existing), on net9.0 and net10.0. `Design.sln`: 107 tests pass on both.
