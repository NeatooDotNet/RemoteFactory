# v1.10.6 — `[AspAuthorize]` Refuses a Caller Who Is Not Signed In

**Released:** 2026-10-13
**Breaking changes:** No. Update the server.

## Overview

A security fix in `Neatoo.RemoteFactory.AspNetCore`. On a class-factory operation, `[AspAuthorize]` let two kinds of refused caller through:
- a caller who was not signed in;
- a caller refused by a policy handler that calls `context.Fail()` without naming a failed requirement.

Both are now refused. Any server whose `/api/neatoo` endpoint admits anonymous requests was exposed. A server whose endpoint already requires an authenticated user (a fallback policy, or `RequireAuthorization` on the endpoint) was exposed only to the second case.

## Bug Fixes

### `[AspAuthorize]` on a class-factory operation allowed refused callers

Class factories call `IAspAuthorize.Authorize` without forbid and convert the returned message to `Authorized`. `Authorized` reads a null or empty message as allowed, so a refusal must never be empty. `AspAuthorize` returned an empty refusal in two places:
- **Authentication did not succeed.** It returned the authentication failure's message. A request with no credentials authenticates to `NoResult`, which carries no failure, so the message was null and the operation ran without evaluating the policy.
- **The policy failed.** It returned the failed requirements joined with commas. A handler that calls `context.Fail()` names none, so the message was empty and the operation ran.

Both now return a refusal: the failure's own message when there is one, otherwise "Not Authenticated" or "Not Authorized". A refused class-factory operation surfaces on the client as `NotAuthorizedException`, as a refusal by a named requirement already did.

Static-factory `[Execute]` and interface-factory methods call with forbid, so they already refused both callers with a 403. Their exception message now says "Not Authenticated" in place of "Forbidden" when there is no failure message.

## What's New

Nothing new in the public API.

## Migration Guide

- Update `Neatoo.RemoteFactory.AspNetCore` on the server. No code changes.
- If a client relied on an anonymous call to an `[AspAuthorize]` class-factory operation succeeding, it now receives `NotAuthorizedException`. Remove the attribute from that operation, or sign the caller in.

## Testing

- `AspAuthorize` without forbid, through ASP.NET Core's own policy pipeline (`AddAuthorization`, `PolicyEvaluator`):
  - an anonymous caller is refused, with a message;
  - a policy whose handler calls `context.Fail()` is refused, with a message;
  - a signed-in caller without the role is refused, and one with the role is allowed.
  - The first two failed before the fix: `HasAccess` was true.
- `Neatoo.RemoteFactory.sln`: 845 unit and 648 integration tests pass (5 skipped, all pre-existing), on net9.0 and net10.0. `Design.sln`: 107 tests pass on both.
