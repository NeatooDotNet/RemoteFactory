# v1.8.0

**Released:** 2026-08-31
**Breaking changes:** No — source that compiles against v1.7.0 continues to compile.

## Overview

`[FactoryEventHandler<T>]` registrations gain a **dispatch phase**, so read-only projection
handlers stop inheriting the in-transaction dispatch contract that was built for atomic write
handlers.

Before this release every handler ran at `Raise`, inside the caller's scope and transaction.
That is right for a handler that must succeed or fail with the write. It is wrong for one that
sends an email, refreshes a cache, or writes a projection — work that has no business holding a
transaction open, and whose failure should not roll back a save that already succeeded.

Three phases now exist. `Immediate` is today's contract and remains the default. `AfterFlush`
is still in-transaction but drains when *you* say so. `AfterCommit` drains after the entry
factory call completes, with no ambient transaction — handler exceptions there are logged and
swallowed, and queued work never runs at all if the entry call failed.

RemoteFactory stays persistence-agnostic throughout. It never flushes and never commits; it
only exposes the drain points where you do.

## What's New

### Dispatch phases

```csharp
[FactoryEventHandler<OrderPlaced>(DispatchPhase.AfterCommit)]
public static partial class OrderProjections
{
    internal static Task Handle(OrderPlaced evt, [Service] IProjectionStore store)
        => store.Apply(evt);          // runs after the save completed; cannot roll it back
}
```

- **`Immediate`** (default) — dispatches at `Raise`, in the caller's scope and transaction.
  Unchanged from v1.7.0. Observes staged, unflushed state.
- **`AfterFlush`** — queued, drained when you call
  `IFactoryEventPhaseCoordinator.DrainAsync(DispatchPhase.AfterFlush)` from inside the factory
  method body, between your flush and your commit. Still in-transaction: a handler exception
  propagates so you can roll back.
- **`AfterCommit`** — queued, drained by the framework when the entry factory call completes.
  No ambient transaction. Handler exceptions are logged and swallowed; the remaining queue
  still runs.

**Cross-phase ordering is a framework guarantee, anchored per drain point.** For work raised
before a given drain point, all `Immediate` handlers complete before any `AfterFlush` handler,
which complete before any `AfterCommit` handler. Code that raises *after* its own `AfterFlush`
drain interleaves that later `Immediate` work between drain points — the guarantee is per drain
point, not a global barrier over the operation.

**Failure semantics key off the drain point, not the phase.** If the entry factory call throws,
queued `AfterFlush` and `AfterCommit` work is discarded without running.

### Consumer-controlled drain

`IFactoryEventPhaseCoordinator.DrainAsync(DispatchPhase.AfterFlush)` drains the `AfterFlush`
queue at the point you choose. It is **fail-open**: handlers you never drain still run, at the
`AfterCommit` point, with a warning (9007) naming the event type — you lose the transaction
placement you asked for, never the handler.

### Opt-in same-event coalescing

```csharp
[FactoryEventHandler<InventoryChanged>(DispatchPhase.AfterCommit, Coalesce = true)]
```

A handler that opts in runs **once per drain** when the same `Equals`-identical event was raised
N times during the entry call. Without the flag, N raises still produce N dispatches. Two
hazards are worth knowing: an event carrying a reference-typed member defeats coalescing
silently (records compare those by reference), and a custom `Equals` can over-collapse. The
surviving dispatch is the **first** raised, and a collapse never erases a fail-open warning.

Cross-event coalescing ("any of these four → one recompute") is deliberately not included;
guard inside the handler.

### Events raised by handlers still relay

Events raised *by* `AfterCommit` handlers reach the client in the same HTTP response's relay
batch, so a projection handler can notify the client without a second round trip.

### New diagnostics

| ID | Severity | Meaning |
|----|----------|---------|
| **NF0504** | Warning | `[FactoryEventHandler<T>]` declared more than once for the same event type on one class. The duplicate is ignored and the first declaration's registration stands; the message names the surviving phase and flag. Stack the attribute for *different* event types, not to re-declare one. |
| **NF0505** | Warning | `Coalesce = true` at `DispatchPhase.Immediate`. `Immediate` dispatches run at `Raise` and are never queued, so there is nothing to coalesce — the flag is inert. Remove it, or defer the handler. |

Both are Warnings rather than Errors, following NF0503's precedent: the declaration compiles and
still produces a working registration, so the build stays green.

## Bug Fixes

Three generator defects, all found by giving the emission fixtures a hostile namespace layout.
Each affects **any** `[Factory]` type, not only phased handlers.

- **Generated code bound to the wrong type when a consumer namespace shadowed ours.** The
  emitted event type, `[Service]` parameter types, and framework tokens were not
  `global::`-qualified, so a consumer namespace shadowing the first segment captured them. This
  is the same latent defect fixed on the registrar attribute in v0.24.1, in the tokens beside it.
- **A handler class whose attributes were split across two partial declarations crashed the
  generator.** Two syntax nodes produced two identical models sharing one hint name, and the
  duplicate `AddSource` threw — surfacing as **CS8785**, which is not scoped to the offending
  class: the generator contributes *nothing*, so every factory in the assembly disappears and
  the consumer sees missing-type errors pointing nowhere near the cause.
- **Delegate and method return types were captured namespace-qualified but unrooted**, so under
  a shadowing namespace they bound to the wrong type — CS0029 on static factories, CS0738 on
  interface factories.

Also: **NF0102's message no longer prints `global::`** on the offending return type.

## Behaviour Notes

**Log event ids 9001–9009 have new meanings.** v1.5.0 deleted the `[Event]` API and freed that
block; this release assigns it to phased dispatch. If you alert on RemoteFactory log ids, re-read
the table in [factory-events](../factory-events.md) — an id that meant one thing at v1.4.0 means
something unrelated now.

**`Internal` phase implementations are public and unsealed.** `FactoryEventPhaseScheduler` and
`FactoryEventPhaseCoordinator` follow the repo's existing convention: the
`Neatoo.RemoteFactory.Internal` namespace conveys "extend at your own risk," not "you may not."
Nothing is cut off. Members there may change in any release.

**One factory call per scope at a time.** Entry-call tracking is per DI scope, not per flow. Two
concurrent flows sharing a scope share one depth counter — the documented limitation, since a
shared scope already shares DbContexts and every scoped service.

## Migration

None required. Handlers without a phase argument behave exactly as before, and the full v1.7.0
test suite passes unmodified.

To adopt phases, add the argument to handlers that should not hold a transaction:

```csharp
// before — runs at Raise, inside the caller's transaction
[FactoryEventHandler<OrderPlaced>]

// after — runs after the entry factory call completes, no ambient transaction
[FactoryEventHandler<OrderPlaced>(DispatchPhase.AfterCommit)]
```

If you use `AfterFlush`, call the coordinator's drain **from inside the factory method body**.
A drain called from outside the factory call never reaches the work, because the queue only
exists while the entry call is active — you will get 9009 at Debug where you called it, and 9007
at Warning where the work eventually ran.
